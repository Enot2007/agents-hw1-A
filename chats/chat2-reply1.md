# Proposal: мини-трекер учебных задач на неделю

## Why

Нужен простой автономный инструмент, чтобы планировать учебные задачи на неделю и видеть прогресс в часах. Он должен работать без сети, CDN, внешних библиотек и API-ключей. Прогресс должен считаться правильно и не зависеть от фильтра.

## What Changes

- Добавляется мини-трекер. Задача содержит поля `id`, `title`, `hours`, `done`.
- Пользователь может добавить задачу, удалить её и переключить `done`. Эти действия меняют данные приложения, а не только разметку.
- Ввод проверяется: название после trim непустое; часы от 0,5 до 24 с шагом 0,5; пустое поле не считается нулём. Ошибка показывается рядом с полем, введённые значения не стираются.
- Итоги: всего часов, выполнено часов, прогресс = round(100 × done / total). Без задач прогресс равен 0%.
- Фильтр меняет только видимый список. Итоги всегда считаются по всем задачам.
- Стартовый пример: «Чтение» 2 ч (done), «Практика» 4 ч, «Повторение» 2 ч. Всего 8 ч, выполнено 2 ч, прогресс 25%.
- Интерфейс читается на ширине 390 px без горизонтального скролла. У всех полей и кнопок есть подписи.
- Необязательно: сохранение в localStorage. Если хранилище недоступно, показывается понятное сообщение, а работа продолжается в памяти.

Есть два варианта поставки, их результат одинаков:
- **A** — один файл `tracker-v2.html`, CSS и JavaScript встроены в него.
- **B** — файлы `index.html`, `styles.css`, `app.mjs`, `domain.mjs`, `tests/acceptance.test.mjs`.

## Capabilities

### New Capabilities
- `tracker`: управление списком учебных задач, валидация ввода, расчёт итогов и прогресса, фильтр видимого списка, адаптивный доступный интерфейс, необязательное локальное сохранение.

### Modified Capabilities
- нет

## Границы (Non-goals)

- Нет сервера, синхронизации, авторизации, аккаунтов и сетевых запросов.
- Не делаем редактирование названия или часов у существующей задачи, сортировку, перетаскивание, даты, дедлайны, категории, несколько недель.
- Фильтр ограничен значениями «Все» и «Активные». Другие значения не требуются.
- Не подключаем сборщики, фреймворки, внешние тестовые библиотеки и CDN.
- На этом этапе пишутся только документы. Код пишется отдельным запросом.

## Impact

- Новые файлы: `tracker-v2.html` в варианте A или пять файлов варианта B.
- Зависимости: нет. Для тестов варианта B используется встроенный `node:test` (Node.js 18+).
- Вариант A открывается напрямую из файла. Варианту B нужен локальный статический сервер, потому что ES-модули через `file://` браузеры блокируют (см. design.md).

### Requirement: Модель задачи и стартовые данные
Трекер MUST хранить задачи как записи `{ id, title, hours, done }`, где `id` уникален, `title` — непустая строка после trim, `hours` — число от 0,5 до 24, кратное 0,5, `done` — boolean. При первом запуске (без сохранённых данных) трекер MUST содержать ровно три задачи в таком порядке: «Чтение» 2 ч done=true, «Практика» 4 ч done=false, «Повторение» 2 ч done=false.

#### Scenario: Стартовые итоги примера
- **WHEN** трекер открыт впервые со стартовым примером
- **THEN** показано: всего 8 ч, выполнено 2 ч, прогресс 25%

### Requirement: Изменение данных действиями пользователя
Добавление, удаление и переключение `done` MUST менять сам массив задач. Интерфейс и итоги MUST перерисовываться по обновлённым данным, а не только по разметке.

#### Scenario: Отметить «Практику» готовой
- **WHEN** у «Практики» в стартовом примере включён признак done
- **THEN** выполнено 6 ч из 8 ч
- **AND** прогресс 75%

#### Scenario: Снять отметку обратно
- **WHEN** у «Практики» done сначала включён, затем выключен
- **THEN** выполнено 2 ч из 8 ч, прогресс 25%

#### Scenario: Добавление корректной задачи
- **WHEN** в стартовом примере добавлена задача «Конспект» на 2 ч
- **THEN** в данных 4 задачи, новая имеет done=false и уникальный id
- **AND** всего 10 ч, выполнено 2 ч, прогресс 20%

#### Scenario: Удаление задачи
- **WHEN** в стартовом примере удалена «Практика»
- **THEN** её нет ни в данных, ни в списке
- **AND** всего 4 ч, выполнено 2 ч, прогресс 50%

#### Scenario: Удаление всех задач
- **WHEN** удалены все задачи
- **THEN** итог 0 ч, выполнено 0 ч, прогресс 0%
- **AND** на странице нигде нет «NaN» или «Infinity»

- **AND** рядом с полем названия видна ошибка, в поле часов осталось «2»

#### Scenario: Пустые часы
- **WHEN** название «Тест», поле часов пустое
- **THEN** задача не добавлена

#### Scenario: Отрицательные часы
- **WHEN** название «Тест», часы −1
- **THEN** задача не добавлена, рядом с полем часов видна ошибка о диапазоне 0,5–24

- **THEN** задача не добавлена, рядом с полем часов видна ошибка

- **WHEN** часы равны «0,5» или «24» при непустом названии
- **THEN** задача добавлена

#### Scenario: Нет задач
- **WHEN** список задач пуст
- **THEN** прогресс 0%, а не NaN% или Infinity%

### Requirement: Фильтр видимого списка
Трекер MUST предоставлять фильтр со значениями «Все» и «Активные» (done=false). Фильтр MUST влиять только на видимый список. Итоги и прогресс MUST считаться по всем задачам.

- **WHEN** в стартовом примере выбран фильтр «Активные»
- **THEN** видны только «Практика» и «Повторение»

# Design: мини-трекер учебных задач

## Context

Нужен автономный клиентский трекер без зависимостей. Варианты A и B реализуют одну и ту же доменную логику. В варианте B она вынесена в `domain.mjs`, чтобы её можно было проверять тестами в Node.js без браузера.

## Goals / Non-Goals

**Goals:** точные расчёты по всем задачам, строгая валидация, единый источник истины (массив задач), рендер из состояния, работа на ширине 390 px.
**Non-Goals:** всё, что перечислено в разделе «Границы» в proposal.md.

## Данные

- `Task = { id: string, title: string, hours: number, done: boolean }`.
- Состояние приложения: `{ tasks: Task[], filter: 'all' | 'active', storageAvailable: boolean }`.
- Стартовые задачи: `[{id:'t1', title:'Чтение', hours:2, done:true}, {id:'t2', title:'Практика', hours:4, done:false}, {id:'t3', title:'Повторение', hours:2, done:false}]`.
- Генерация id: `'t' + (максимальный числовой суффикс среди существующих id + 1)`, или счётчик. `crypto.randomUUID` не используется, потому что через `file://` (вариант A) он может быть недоступен вне secure context.
- Обновления неизменяемые: доменные функции возвращают новый массив, приложение заменяет `state.tasks` и вызывает `render()`.

## Доменные функции (domain.mjs в B, такой же встроенный блок в A)

- `createInitialTasks(): Task[]`.
- `parseHours(raw: string)` возвращает `{ ok: true, value } | { ok: false, code }`:
  1. `s = String(raw ?? '').trim()`. Если `s === ''`, результат `code: 'empty'` (не ноль).
  2. Запятая заменяется точкой. Строка должна соответствовать `^-?\d+(\.\d+)?$`, иначе `code: 'nan'`. Так отсекаются `abc`, `1e1`, `Infinity`.
  3. `n = Number(s)`. Если `n < 0.5 || n > 24`, результат `code: 'range'` (это покрывает 0 и отрицательные).
  4. Если `!Number.isInteger(n * 2)`, результат `code: 'step'`.
- `validateTaskInput({ title, hours })` возвращает `{ ok, value?: {title, hours}, errors: { title?, hours? } }`. Название проверяется по `title.trim() !== ''` и сохраняется уже обрезанным. Ошибки обоих полей собираются за один вызов.
- `addTask(tasks, input, id)` вызывает валидацию. При ошибке массив не меняется и возвращаются ошибки. Новая задача получает `done: false`.
- `removeTask(tasks, id)`, `toggleTask(tasks, id)`.
- `filterTasks(tasks, filter)`: для `'all'` возвращает все задачи, для `'active'` — задачи с `done === false`.
- `summarize(tasks)` возвращает `{ totalHours, doneHours, progress }`.

## Расчёты

- `totalHours = Σ hours` по **всем** задачам. `doneHours = Σ hours` по задачам с `done`.
- `progress = totalHours > 0 ? Math.round(100 * doneHours / totalHours) : 0`.
- Часы кратны 0,5 и точно представимы в двоичной плавающей точке, поэтому суммы точны.
- `summarize` всегда получает полный `state.tasks`, никогда результат `filterTasks`.
- Контрольные значения:

| Состояние | total | done | progress |
|---|---|---|---|
| Старт | 8 | 2 | 25% |
| Практика отмечена готовой | 8 | 6 | 75% |
| Фильтр «Активные» (из старта) | 8 | 2 | 25% |
| Удалена «Практика» | 4 | 2 | 50% |
| Добавлен «Конспект» 2 ч | 10 | 2 | 20% |
| Пусто | 0 | 0 | 0% |

- Часы выводятся с десятичной запятой: `toLocaleString('ru-RU')`, например «2,5 ч».

## Интерфейс

- Форма: `<label for>` у полей «Название» и «Часы», кнопка «Добавить». Поле часов — `type="text" inputmode="decimal"`. Это решение принято, чтобы валидатор получал сырую строку: при `type="number"` пустое и нечисловое значение одинаково приходят как `''`, а ввод запятой зависит от локали браузера.
- Ошибки: `<p id="…-error">` сразу под полем, у поля `aria-invalid="true"` и `aria-describedby`. При ошибке значения полей не очищаются. После успешного добавления форма очищается, ошибки снимаются.
- Фильтр: группа радиокнопок в `<fieldset>` с `<legend>Фильтр</legend>`.
- Строка задачи: чекбокс с подписью вида «Выполнено: Практика», текст названия и часов, кнопка «Удалить» с `aria-label="Удалить: Практика"`.
- Итоги: «Всего: 8 ч · Выполнено: 2 ч · Прогресс: 25%» и `<progress max="100">` с подписью. Область итогов помечена `aria-live="polite"`.
- Название выводится только через `textContent`, а не `innerHTML`, чтобы исключить внедрение HTML.
- Вёрстка: `<meta name="viewport" content="width=device-width, initial-scale=1">`, `box-sizing: border-box`, одна колонка, `max-width: 100%`, `overflow-wrap: anywhere` для названий, никаких фиксированных ширин больше 390 px. Минимальная высота кнопок около 44 px.

## Хранилище (необязательно)

- Ключ `tracker-v2.tasks`, значение — JSON массива задач.
- Все обращения (включая само чтение `window.localStorage`) обёрнуты в `try/catch`. При ошибке `storageAvailable = false`, на странице показывается сообщение «Хранилище недоступно — изменения сохранятся только до закрытия страницы», дальше работа идёт в памяти.
- Загрузка: если ключа нет, используется стартовый пример. Если там валидный массив (в том числе пустой), он и загружается. Если JSON битый или записи не проходят валидацию, используется стартовый пример и показывается сообщение о сброшенных данных.
- Сохранение выполняется после каждого изменения `tasks`. Смена фильтра не сохраняется.

## Варианты поставки

- **A:** `tracker-v2.html` содержит `<style>` и обычный `<script>` (не module). Открывается через `file://`.
- **B:** `index.html` подключает `styles.css` и `<script type="module" src="app.mjs">`. `app.mjs` импортирует `domain.mjs` и отвечает только за DOM, события и хранилище. `domain.mjs` не обращается к DOM и `localStorage`. Тесты `tests/acceptance.test.mjs` используют `node:test` и `node:assert/strict` и запускаются командой `node --test tests/`.

## Risks / Trade-offs

- Вариант B через `file://` не загрузит модули, потому что браузер блокирует их по CORS. Нужен локальный статический сервер, например `python3 -m http.server`. Сервер должен отдавать `.mjs` с MIME `text/javascript`; это нужно проверить при реализации.
- Логика в A дублирует `domain.mjs`. Есть риск расхождения, поэтому чек-лист ручных проверок общий для обоих вариантов.
- Поведение localStorage на `file://` различается между браузерами. Это закрыто запасным режимом работы в памяти.
- Тесты B покрывают только доменную логику. DOM, вёрстка на 390 px и доступность проверяются вручную.
